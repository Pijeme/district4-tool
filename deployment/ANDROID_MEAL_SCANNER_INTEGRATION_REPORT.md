## 2. Actual identity and QR format
Events have an integer SQLite id and a globally random uuid4().hex key. event_attendees.key is a random uuid4().hex string allocated as the browser form key, persisted as the PRIMARY KEY and reused as the ticket identifier. There is no separate ticket table. event_attendees.event_id links to registration_events.id. The per-event number is allocated transactionally only after live camera completion, restarts at 1 for each event, and is never a global ticket identifier.
QR contents are exactly https://iowod4tool.coresite.pro/event-registration/ticket/<32 lowercase hex attendee key>. The origin currently comes from CCM_BASE_URL with /ccm removed; this constant does not make Event tickets CCM records. Parse the allowed scheme/host/path locally and extract the ticket key, then verify it against the selected event's downloaded roster. Parsing is NOT proof of validity or payment. Preserve this URL format and existing keys.
GET event_ticket returns HTML with name, area, church and event for complete, nondeleted registrations. It does not redeem a meal or require payment. There is no automatic Event ticket expiration. Deleting an attendee/event revokes its lookup; archiving an event does not. Public lookup is not a protected roster API.

## 3. Database and transactions
The authoritative database is DATA_DIR/app_v2.db (project-root app_v2.db if DATA_DIR is unset). See BASELINE_SCHEMA.sql and the event_tables source for exact fields, primary keys, declared foreign keys, unique indexes and additive columns. Important: complete means public details + camera saved; paid, printed and released are separate booleans. A fully processed registration is paid AND printed AND released. Foreign keys are declared; get_db does not currently enable PRAGMA foreign_keys. Do not assume cascading deletes.
BEGIN IMMEDIATE protects number allocation and event edits. Per-record and global file locks serialize backup retries across workers. Revisions protect stale admin updates. Updated timestamps are not a globally monotonic change feed, and deleted records can eventually be purged after Sheets deletion, so incremental APIs need explicit tombstones or authoritative replacement snapshots.

## 4. Google integration
get_gs_client resolves service-account credentials through runtime_config.google_credentials. Credential file/JSON/base64 contents are intentionally absent. Spreadsheet: District4 Data; registration worksheet: Event Registration. Columns: Name | Bday | Contact # | Area | Church Name | Church Address | Pastor | Date created | Paid | Print | Release | Event. Ticket keys are NOT exported into these columns. Date created is original registration creation, never backup time. Local SQLite is authoritative; Sheets is an explicit backup and does not overwrite local records.
Backup Data uploads only the generated printable ID, verifies its Drive checksum/size, writes RAW Sheets values, rereads and confirms the complete row. The portrait remains local. Existing id_drive_id/id_backup_hash allow retry reuse. Full-table reads/writes happen per attendee; no meal export exists in this baseline. A failed or interrupted backup retains local data and confirmed references; matching event/creation snapshots makes retry append/update idempotent. Existing file-upload token auth is for Drive only, NOT for Android roster/claims APIs.

## 5. Existing routes and auth
BASELINE_ROUTES.json inventories methods, paths, function names and source lines. Public: GET /event-registration; POST /details with browser ownership + CSRF; GET/POST /photo/<key> with owner/session + CSRF on mutation; POST /cancel/<key> only own unfinished record with confirmation; GET /ticket/<key> is public HTML. Admin routes use a four-hour shared-password session and CSRF; its password is redacted. Developer event create/edit/delete additionally checks the signed-in developer against the Accounts cache. POST /admin/status/<key> accepts field=paid|printed|released, value=0|1, revision, csrf_token, and confirm=yes when reverting paid/released. Success: {ok:true,revision:N,<field>:0|1}; conflicts 409. POST /admin/backup returns {ok:true,keys:[...]}; POST /admin/backup/<key> returns {ok:true,clean:boolean,pending_deletions:N}, possibly removed:true. GET print/image routes are session protected. The old POST /photo/<key>/backup intentionally returns 409 and never uploads.
No baseline JSON roster, master authentication, meal schedule, claim, correction, Bluetooth pairing or synchronization API exists. Do not code Android against the existing browser form routes or embed the shared admin password.

## 6. Android architecture and agreed policy
Only MASTER contacts Flask. SLAVE pairs with MASTER over Bluetooth, sends scan requests, and displays results; no slave website credentials. MASTER makes authoritative local atomic meal decisions while offline. Any paid delegate is meal-eligible; printed/released do not control meals. MASTER creates meal sets/sessions; the first sync imports them into the selected website event. The website never invents breakfast/lunch/dinner slots. Each meal session needs a stable app-generated ID, a display name and service date. MASTER should have one local unique constraint on event+meal_session+ticket for accepted claims. Store all attempts/audits, including disagreements and corrections.

## 7. Proposed server API (NOT baseline implementation)
Use separate HTTPS bearer credentials for MASTER, not the browser password, Drive upload token or QR ticket. Proposed prefix /event-registration/api/v1. GET /events; GET /events/<event_key>/delegates; GET /events/<event_key>/changes; POST /events/<event_key>/meal-sets; POST /events/<event_key>/claims; POST /events/<event_key>/audit; GET /events/<event_key>/sync-status. Provide stable master-generated batch, claim and audit IDs; transactionally persist canonical payload hashes and acknowledgements so lost responses can be retried. Reusing an ID with different content must never overwrite history. Reject unpaid/unknown/cross-event tickets and duplicate accepted meal claims while preserving the attempt for review. Roster replacement snapshots are safer than timestamp-only deltas with this existing deletion model. Local Bluetooth transport, pairing and Android SQLite remain Android-only responsibilities.
These are proposals until IMPLEMENTED_API.md and the final website source snapshot are added after implementation. Confirm the final contract before generating Kotlin DTOs.

## 9. Required website changes / compatibility
Two admin lists and totals; full protected delegate details; meal tables and protected history view; MASTER-only JSON API with imported meal definitions, idempotent transactional claims/audits, private no-store responses and clear errors; explicit Google meal-record backup. Preserve existing QR links and numbering. No direct remote SQLite access. Keep birthdays/contact/admin passwords out of QR and Android roster unless a later explicit requirement justifies extra data. MASTER must refresh paid/revoked status; offline decisions use its cached roster and later conflicts must be visible rather than erased.

## 10. Remaining integration work
Specify Android Bluetooth permissions, protocol framing, discovery, pairing, reconnect and a single active MASTER strategy in the Android project. The website cannot prevent two disconnected masters from both serving a meal in real time; use one master and serialize Bluetooth scan requests there. Website conflict handling is reconciliation. API deployment/auth provisioning and mobile tests still require the actual master app. No real attendee data, database, .env, service-account file or secret token is included.
